# 从一堆坐标，到一张「13 年跑过的地方」词云

> **这是什么**：一条把**旧运动手表的 GPS 记录**变成**可看、可验、可发布的地图与词云**的完整操作流程。
> 2026-10-25 用它做完了「十年前那只表，记了 387 次我忘了的跑步」，从导数据到出交付页跑了 9 步、4 秒。
> **给谁看**：手里有佳明/松拓/华为等运动手表导出数据、想把自己十几年的跑步记录做成一张图的人。
> **一句话前提**：老设备往往只记坐标、不记地名。地名是「查」出来的，不是「猜」出来的。
>
> ⚠️ **先说清楚边界**：本文给的是**方法与判据**（怎么判、门槛定在哪、哪里会错）。文末提到的脚本是本机私有工具，带着个人数据路径，**不随本文发布**。照着本文自己写，核心逻辑约 200 行 Python。

## 〇、先看这条路能走到哪

一只 2014 年买的 Garmin fēnix 2，戴了三年，记了 387 次跑步，**地名那一栏全是空的**——只有时间、坐标、距离。

做完之后拿到的东西：

| 产物 | 长什么样 | 有什么用 |
|---|---|---|
| 城市清单 | 19 个地方，各自次数、距离、第一次去的年份 | 「原来那几年我在这些地方跑过」 |
| 词云 | 城市 + 年份 + 时段，字号＝次数 | 一眼看出那几年的生活重心 |
| 24 小时分布 | 几点出门，一看就懂 | 作息是能被数据还原的 |
| 热力图 | 全国点位热力（**只自己看，不公开**） | 直观，但内嵌真实坐标 |
| 交付页 | 单文件 HTML，零联网、零坐标 | 能发给别人看的版本 |

**整条流程 9 步，跑完约 4 秒**（不含首次反查接口调用）。反查一次之后，后面全是本地计算。

## 二、六步主流程

### 第 1 步 · 把数据按「设备」切开

先说一件最容易忽略的事：**一只表 = 一个 deviceId**。老表和新表的数据混在一起，统计必错。

```python
import json, collections
data = json.load(open("2013-2026.json", encoding="utf-8"))

# 先看有哪些设备、各多少条、时间跨度
cnt = collections.Counter(r.get("deviceName") for r in data)
for name, n in cnt.most_common():
    print(name, n)
```

**验收**：设备名、条数、起止日期三样对得上。这一步不做，后面全乱。

---

### 第 2 步 · 只留跑步，别把游泳算进来

佳明的 `activityType.typeKey` 有几十种。做「跑过的地方」就只算跑：

```python
RUN_KEYS = {"running", "indoor_running", "treadmill_running"}
runs = [r for r in data
        if (r.get("activityType") or {}).get("typeKey") in RUN_KEYS]
```

> 🚨 **这一步我踩过。** 不按类型过滤，直接把「有城市名的记录」拿来统计，会多出 43 条游泳、力量、登山——城市数不变，但次数全错（1,889 变成 1,932，某市 770 变成 785）。**「去重」之外，还有一层「按运动类型过滤」，两个都要过。**

---

### 第 3 步 · 去重：同一次跑步可能被两只表各记一遍

换表那阵子，新旧两只表同时戴过。同一次跑步被记录两次（时间差几秒、距离差几十米），直接汇总就重复计数。

**判重规则**（可照抄）：

```python
# 起跑时间相差 ≤ 120 秒 + 距离相差 ≤ 2% → 判为同一次
def same_run(a, b):
    dt = abs(seconds_between(a["startTimeLocal"], b["startTimeLocal"]))
    da = a.get("distance") or 0
    db = b.get("distance") or 0
    return dt <= 120 and da and db and abs(da - db) / max(da, db) <= 0.02
```

**保留谁**：按设备优先级留一条，新的留、旧的删。

```python
DEVICE_PRIORITY = ["飞5X Plus", "飞3 HR", "飞2"]   # 越靠前越优先
```

**验收**：全库 2,199 条 → 去重后 2,171 条，重复 28 对。差值要能对上：
某市 −17、另一个市 −6，合计 −23 条跑步 + 5 条非跑步 = 28。**对不上就是规则写错了。**

> 🚨 **别只去重一次就完事。** 第一次只处理了跑步，后来发现跳绳、登山也有 5 对重复，得补扫一遍全类型。**去重脚本要能对「全部运动类型」跑，不能只写 `WHERE type='running'`。**

---

### 第 4 步 · 反查前先聚类，200 米归一个点

逐条打接口是浪费：三年 300 多次跑步，其实只发生在十几个场地。

**做法**：把每条记录的起终点坐标按 **200 米**归簇，每个簇只问一次。

```
387 条记录 → 373 条有坐标 → 归成若干跑点簇 → 每簇取簇心问一次
```

**为什么是 200 米**：小于 100 米会把一个操场的两头分成两簇，大于 500 米会把一个区的两片跑点合并。200 米是试出来的，跑完对得上原始地名。

---

### 第 5 步 · 反查：给置信分级，D 级不落库

这一步是整条流程的核心。**不是「查一下返回什么就写什么」，而是四级置信**：

| 级别 | 距离城市中心 | 处理 |
|---|---|---|
| A | ≤ 2 km | 建成区核心，直接采用 |
| B | 2–8 km | 近郊/开发区，直接采用 |
| C | 8–25 km | 可能越界（邻县、山区），标「待核」 |
| D | > 25 km | **不判定，坐标留原样，不硬塞一个城市** |

```python
city, dist_m, grade, _, province = predict(lat, lng)
if grade == "D":
    city_name = ""          # 留空，不猜
    geocode_grade = "D"     # 留审计痕迹
```

**结果**：387 条里补出 368 条地名，**19 条判不了就留空**。

> 「留空」比「猜一个」值钱。公开作品里出现一个错城市，整份数据的可信度就没了。

### 第 6 步 · 拿真数据验一遍（这条最不能省）

**问题**：新建的表没有任何地名，怎么证明你的反查是对的？

**答案**：拿**后来**的表当标尺。新表固件升级了，会记 `locationName`，这些记录同时有「地名」和「坐标」——**地名就是标准答案**。

```python
# 只用「既有地名、又有坐标」的记录做验证集
val = [r for r in runs if r.get("locationName") and r.get("startLatitude")]
```

然后**只把坐标**丢给引擎，不许看标准答案；再逐条比对。

| 项 | 实测值 |
|---|---|
| 验证集 | 1,524 条 |
| 对 | 1,517 条 |
| 错 | 7 条 |
| 准确率 | **99.54%** |
| 门槛 | **99%**（写死在脚本里，跑不过整批中止） |

**7 条错的是什么**：3 条引擎判 `None`（坐标超 25km，D 级不猜）；4 条是「北京市」这类带「市」字的写法差异。

> 🚨 **门槛要提前定，不能验完再定。** 验完才定门槛，等于给结果量身裁衣。这条线写在代码常量里：`EXPECT_ACC = 0.99`。

## 三、出图：词云、热力图、交付页

### 3.1 词云怎么排才不像「随机撒字」

| 词类 | 取值 | 颜色 | 字号 |
|---|---|---|---|
| 城市 | 该城市次数 | 暖黄 | `13 + 44 × (n/最大值)^0.42` |
| 年份 | 该年次数 | 青 | 同式 |
| 时段 | 该时段次数 | 紫 | 同式 |

- **开 0.42 次方的幂**：不开方，第一名会把其他词压成看不见的小字；开 1 次方，差距又太平均。
- **固定随机种子**：`random.Random(42).shuffle(words)`。每次生成顺序一致，截图可复现。
- **字重和透明度也随次数走**：`opacity = 0.42 + 0.58 × (n/最大值)^0.35`。

### 3.2 热力图的内嵌数据陷阱

地图页用的是单文件 HTML，数据**内嵌**在页面里：

```javascript
const VZ = {"points": [...], "cities": [...], "meta": {...}}
```

> 🚨 **它不是读 json 文件的。** 改了 `可视化数据.json` 而没重新注入 `const VZ`，页面还是旧数据——我踩过，导出的 json 是新的，地图上还是 1,912 个点。
> **正确做法**：写完 json 后，脚本定位 `const VZ = ` 那一行整行替换，并校验 `</html>`、地图库名、坐标转换函数仍在。

### 3.3 交付页：只放聚合，一条坐标都不放

对外页的每一行都是「城市 → 次数 / 距离」，**没有任何经纬度**。

原因很直接：**一串跑步起点坐标，等于住址。**

机器自检（7 项，全 0 才能出门）：

| 检查 | 阈值 |
|---|---|
| `http(s)://` | 0 |
| `src=` 引用 | 0 |
| `fetch` / `XMLHttpRequest` | 0 |
| 本机路径 `C:/Users` | 0 |
| 用户名 | 0 |
| 精确坐标对（`31.xxxx, 121.xxxx`） | 0 |
| 手机号 | 0 |

## 四、验收：怎么证明「这份数据可以发」

四道门，缺一不可：

| 门 | 怎么验 | 不过怎么办 |
|---|---|---|
| ① 准确率 | hold-out 1,524 条 ≥ 99% | 整批中止，一个字段都不写 |
| ② 口径 | 统计只走「去重后视图」，不看原始表 | 数字对不上就是读错表 |
| ③ 幂等 | 连跑两次，产物 sha256 一致 | 不一致说明有随机或时间依赖 |
| ④ 隐私 | 7 项正则全 0 | 有一项不为 0 就不许发 |

**幂等怎么验**：

```bash
python run_task.py && sha256sum out/data.json > /tmp/a
python run_task.py && sha256sum out/data.json > /tmp/b
diff /tmp/a /tmp/b      # 必须无输出
```

## 五、六个坑（都踩过，按疼的程度排）

**1. 两张表，两个口径，数字差 40 条**

建库时同时留了「去重前」和「去重后」两套表。统计脚本读错了那张，导致地图 1,912 点、文章的 1,889 对不上，一度以为「文章数字过期了要改」。

> **判据**：看表里有没有 `scope` 字段标注口径。没有标注的，一律不当对外数字用。

**2. 时区：两个时间字段，差 8 小时**

手表对同一次跑步存 `startTimeLocal`（本地）和 `startTimeGMT`（UTC）。

| 口径 | 21 点后 | 12–13 点 | 峰值 |
|---|---:|---:|---|
| 本地时间 | 227 | 3 | 22 点 118 次 |
| UTC | 83 | 104（13–14 点合计 214） | 14 点 123 次 |

**按 UTC 读，全部夜跑会搬到午休时段。** 判断方法不用查文档，看分布就行：哪种口径让「227 次跑在上班时间」，那种就是错的。

**3. 年份标签用了「累计」而不是「当年」**

年表上写「2014 · 某市 171」，但那年总共才跑 50 次。原因是标签取了「该城市总次数」。改成当年次数才对。

**4. 只跑 1 次的条形宽度 0.6%，看不见**

`width: 0.6%` 在 800px 容器里只有 4.8px。加 `min-width: 3px` 解决。**可视化里的「看不见」不是数据问题，是渲染问题。**

**5. 空字符串不是 NULL**

`city_name` 有 244 条是 `''`（室内跑没 GPS）。`WHERE city_name IS NOT NULL` 抓不到它们，会把空串当成第 40 个城市。必须 `city_name <> ''`。

**6. 设备 ID 类型不一致**

数据库里 `device_id` 存成了字符串 `'3890733124'`，原始 JSON 里是整数 `3890733124`。用 `in` 直接比，一条都匹配不上——**而且不会报错，只会静默返回空**。

> 教训：任何「按 ID 关联」之后，都加一句断言——**样本数必须等于预期条数，否则不许往下走**。

## 六、频率：多久跑一次

| 场景 | 频率 | 理由 |
|---|---|---|
| 新增了活动数据 | 导完就跑一次（4 秒） | 全流程幂等，跑多少次结果一样 |
| 只改可视化样式 | 不用重跑反查，加 `--skip-geocode` | 省掉接口调用 |
| 只想体检不动文件 | `--check` | 只看准确率和口径，不写库 |
| 年度归档 | 一年一次 | 13 年数据跑完才 4 秒，不怕重跑 |

**唯一要注意**：别在数据源正在写入的时候跑（比如 Garmin Connect 正在同步）。先确认导出文件大小不再变化。

## A4 · 我犯过的错，都记在这

**错 1：把「去重前后」说反了。**
10-24 晚核对数字，直接查了 `activity`（去重前的表），得出「文章 1,889 应改成 1,912、387 应改成 388、81.7% 应改成 81.9%」，还写成结论交给老板。次日追查 `city_stat` 与 `city_stat_v2`，确认**文章数字全对，是我读错了表**。

> 教训：核对数字前先确认这张表是什么口径。**别拿子集或未去重表当全量。**

**错 2：交付页的 json 更新了，地图没变。**
